# ISP workspaces and tenant setup

Each ISP operates in a tenant workspace. Staff sign up at `/signup` and are guided through ISP and captive portal naming, Daraja payment setup, and MikroTik provisioning at `/get-started`. Workspace sessions are opaque, HTTP-only cookies; changing an `x-tenant-id` header cannot change the selected workspace. Each user can create more than one workspace and switch between memberships.

## Deploy

1. Apply all migrations in `supabase/migrations`, including `20261004120000_make_multitenant.sql`, before deploying the tenant-aware application. Existing billing, RADIUS, and provisioning rows remain assigned to the `default` workspace.
2. Keep `DATABASE_URL` configured on the server. For Vercel, use Supabase's **Transaction pooler** connection string (port 6543), not the Session pooler or direct database connection. The app limits each serverless process to one short-lived pooled connection, but the transaction pooler is still needed when Vercel runs many function instances. Account creation, sessions, workspace selection, billing, and password reset require the database. New passwords must be at least 6 characters and contain an uppercase letter, a number, and a symbol (maximum 128 characters). Email-and-password sign-in and signup work without Google OAuth credentials. To enable password-reset email, set the server-side `RESEND_API_KEY` to a Resend API key, `PASSWORD_RESET_FROM` to a sender address verified in Resend (for example, `LKTECH <noreply@example.com>`), and `APP_URL` to the app's canonical origin (for example, `https://billing.example.com`). In local development, use `http://localhost:3000` for `APP_URL`. Apply `20261004140000_add_password_reset_tokens.sql` before deploying password reset. Reset links are single-use and expire after 30 minutes; resetting a password revokes the user's existing sessions.
3. Google sign-in is optional and is not shown on the login/signup pages by default. To enable it later, first apply `20261004130000_add_google_signin.sql`, then configure a Google OAuth 2.0 web application in Google Cloud Console and complete its consent-screen setup (publish the app or add each tester as a test user). Add the callback URI `https://<your-host>/api/auth/google/callback` to the OAuth client's authorized redirect URIs. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and the exact `GOOGLE_REDIRECT_URI` as server-only environment variables in every deployment environment. For local development, if `GOOGLE_REDIRECT_URI` is unset, the app derives it from the local origin; this project uses `http://127.0.0.1:3000/api/auth/google/callback`, which must also be registered as an authorized redirect URI. If using a different local host or port, set and register that exact callback URI.
4. To grant the existing operator access to migrated `default` workspace data, set `DEFAULT_TENANT_OWNER_EMAIL` to that operator's email before they create their first account through `/signup`. Only that exact email can claim the default workspace during signup. Without this setting, new signups create new isolated workspaces and existing rows stay in `default`.
5. Set `TENANT_SECRETS_ENCRYPTION_KEY` to a securely generated, stable 32-byte key (64 hexadecimal characters or base64). For example, generate one locally with:

   ```powershell
   node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
   ```

   Store it as a server-side production secret. Do not commit it, expose it as a `NEXT_PUBLIC_` variable, or change it without decrypting and re-encrypting every workspace's payment credentials.
6. Each workspace owner opens **Billing → Payment settings**, chooses the Daraja environment, and saves that ISP's consumer key, consumer secret, shortcode, passkey, and HTTPS callback URL. Credentials are encrypted with AES-256-GCM before storage. The callback URL must point to `/api/hotspot/daraja/callback` on this deployment. Secrets are never returned to the browser.
7. Give each captive portal its own workspace slug. Use a workspace subdomain where available, or add `?tenant=<workspace-slug>` to the portal URL. For example, `https://billing.example.com/hotspot?tenant=acme-network`. The provisioned MikroTik `login.html` opens the `/hotspot` subscription experience and carries the workspace, client MAC, and a return link to the router login. After purchase, customers can return to the captive sign-in form and enter the supplied credentials. The portal carries the workspace through package selection, checkout, reconnect, payment polling, and roaming API calls. Public tenant selection is for customer-facing portal requests only; it does not grant staff dashboard access.
8. For the guided MikroTik setup to create scripts, configure `PROVISIONING_ADMIN_KEY` (at least 32 characters), `RADIUS_SERVER_ADDRESS` (publicly reachable IPv4 address), `RADIUS_SHARED_SECRET` (16–64 letters, numbers, or hyphens), and `PROVISIONING_BASE_URL` (the app's HTTPS origin). In production the workspace owner must enter the provisioning key in the setup flow. The wizard only reports the router live after RouterOS applies the service script and confirms it back to the app. Existing routers must re-fetch the hotspot files to receive the subscription-portal redirect.
9. To reconcile direct M-Pesa PayBill transfers, configure `C2B_CALLBACK_SECRET` as a random URL-safe server-only secret of at least 32 characters. **Payment settings** displays the workspace-specific validation and confirmation URLs to register for that Daraja shortcode; callback tokens are derived per tenant and the master secret is never sent to the browser. The confirmation endpoint matches the generated PPPoE account number and exact current-plan amount, extends expiry, and updates RADIUS atomically. Other payments are kept in **Billing → Payments** for an operator to match; a mismatched amount cannot activate service.
10. Set `CRON_SECRET` to a different random URL-safe secret of at least 32 characters. The included Vercel cron calls `/api/cron/expire-customers` daily at midnight UTC to mark expired accounts in the dashboard, which is compatible with Vercel Hobby. FreeRADIUS `Expiration` rules prevent new authentication at the configured expiry time; the daily job updates the dashboard status. Forcibly disconnecting already-established sessions requires a separate MikroTik/RADIUS CoA configuration.

The legacy `MPESA_*` environment configuration remains available only to the existing `default` workspace until its owner saves tenant-specific credentials. Newly created workspaces must configure their own Daraja account before paid checkout is available.

For subscriber operations, the **Subscribers** view supports tenant-scoped creation, manual suspension, and activation/renewal. New dashboard-created RADIUS logins start suspended with an `Auth-Type := Reject` rule; activate the account with a future expiry before service begins. Suspension adds the same reject rule; activation updates the expiry and removes it. STK callback payments and reconciled PayBill transfers update the account and expiry transactionally.

## Isolation

Staff API operations resolve tenant IDs from a live server-side session and membership. Package catalogs, purchases, customer records, RADIUS check/reply entries, portal branding, payment sessions, and router provisioning tokens are stored and queried with tenant ownership. Public portal routes resolve an active workspace by slug and scope all lookups to it. Unknown or inactive workspace slugs are rejected.

The current staff signup flow creates workspace owners; membership and session tables support additional roles and multiple memberships. Google sign-in requires a verified Google email; a verified Google identity can be linked to an existing account with the same email. This change does not add invitations or email verification.
