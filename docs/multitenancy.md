# ISP workspaces and tenant setup

Each ISP operates in a tenant workspace. Staff sign up at `/signup` and are guided through ISP and captive portal naming, Daraja payment setup, and MikroTik provisioning at `/get-started`. Workspace sessions are opaque, HTTP-only cookies; changing an `x-tenant-id` header cannot change the selected workspace. Each user can create more than one workspace and switch between memberships.

## Deploy

1. Apply all migrations in `supabase/migrations`, including `20261004120000_make_multitenant.sql`, before deploying the tenant-aware application. Existing billing, RADIUS, and provisioning rows remain assigned to the `default` workspace.
2. Keep `DATABASE_URL` configured on the server. For Vercel, use Supabase's **Transaction pooler** connection string (port 6543), not the Session pooler or direct database connection. The app limits each serverless process to one short-lived pooled connection, but the transaction pooler is still needed when Vercel runs many function instances. Account creation, sessions, workspace selection, billing, and password reset require the database. New passwords must be at least 6 characters and contain an uppercase letter, a number, and a symbol (maximum 128 characters). Email-and-password sign-in and signup work without Google OAuth credentials. To enable password-reset email, set the server-side `RESEND_API_KEY` to a Resend API key, `PASSWORD_RESET_FROM` to a sender address verified in Resend (for example, `LKTECH <noreply@example.com>`), and `APP_URL` to the app's canonical origin (for example, `https://billing.example.com`). In local development, use `http://localhost:3000` for `APP_URL`. Apply `20261004140000_add_password_reset_tokens.sql` before deploying password reset. Reset links are single-use and expire after 30 minutes; resetting a password revokes the user's existing sessions.
3. Google sign-in is optional and is not shown on the login/signup pages by default. To enable it later, first apply `20261004130000_add_google_signin.sql`, then configure a Google OAuth 2.0 web application in Google Cloud Console and complete its consent-screen setup (publish the app or add each tester as a test user). Add the callback URI `https://<your-host>/api/auth/google/callback` to the OAuth client's authorized redirect URIs. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and the exact `GOOGLE_REDIRECT_URI` as server-only environment variables in every deployment environment. For local development, if `GOOGLE_REDIRECT_URI` is unset, the app derives it from the local origin; this project uses `http://127.0.0.1:3000/api/auth/google/callback`, which must also be registered as an authorized redirect URI. If using a different local host or port, set and register that exact callback URI.
4. To grant the existing operator access to migrated `default` workspace data, set `DEFAULT_TENANT_OWNER_EMAIL` to that operator's email before they create their first account through `/signup`. Only that exact email can claim the default workspace during signup. Without this setting, new signups create new isolated workspaces and existing rows stay in `default`.
5. Set `TENANT_SECRETS_ENCRYPTION_KEY` to a securely generated, stable 32-byte key (64 hexadecimal characters or base64). For example, generate one locally with:

   ```powershell
   node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
   ```

   Store it as a server-side production secret. Do not commit it, expose it as a `NEXT_PUBLIC_` variable, or change it without decrypting and re-encrypting every workspace's payment credentials.
6. Each workspace owner opens **Billing → Payment settings**, chooses the Daraja environment, and saves that ISP's consumer key, consumer secret, shortcode, passkey, and HTTPS callback URL. Credentials are encrypted with AES-256-GCM before storage. The callback URL must point to `/api/hotspot/daraja/callback` on this deployment. Secrets are never returned to the browser.
7. Give each captive portal its own workspace slug. Use a workspace subdomain where available, or add `?tenant=<workspace-slug>` to the portal URL. For example, `https://billing.example.com/hotspot?tenant=acme-network`. The provisioned MikroTik `login.html` opens the `/hotspot` subscription experience and carries the workspace, client MAC, and a return link to the router login. After purchase, customers can return to the captive sign-in form and enter the supplied credentials. The portal carries the workspace through package selection, checkout, reconnect, payment polling, and roaming API calls. Public tenant selection is for customer-facing portal requests only; it does not grant staff dashboard access.
8. For the guided MikroTik setup to create scripts, configure `PROVISIONING_ADMIN_KEY` (at least 32 characters), `RADIUS_SERVER_ADDRESS` (publicly reachable IPv4 address), `RADIUS_SHARED_SECRET` (16–64 letters, numbers, or hyphens), and `PROVISIONING_BASE_URL` (the app's HTTPS origin). The guided provisioning script requires RouterOS 7.1 or newer. In production the workspace owner must enter the provisioning key in the setup flow. The initial download link expires after 15 minutes; once the router reports the first setup script applied, the service-configuration step receives a fresh 24-hour window. That initial script reports the router's interface addresses so the service step can reject a Hotspot subnet that overlaps a selected WAN. Choose a private Hotspot subnet distinct from the WAN (for example, `172.31.0.0/24` when WAN uses `192.168.88.0/24`), keep the WAN port out of the subscriber bridge, and include the intended local management port. Move an active WAN DHCP client off the subscriber bridge before applying services; the wizard rejects using the same bridge for both roles. Provisioning scripts are snapshots: if a script was prepared before changing the subnet defaults or conflict checks, create a new provisioning token and follow the wizard from its initial script instead of reusing the old service script. The wizard only reports the router live after RouterOS applies the service script and confirms it back to the app. Existing routers must re-fetch the hotspot files to receive the subscription-portal redirect. Router monitoring is not installed by the provisioning script.
9. Apply `20261005150000_add_router_monitoring.sql` before deploying router monitoring. **Network → Devices → Routers** lists the configured network sites. Select a site and choose **Set up automatic monitoring** to generate a one-time authenticated RouterOS script. Copy/paste it into the MikroTik terminal once; it replaces the old monitor scheduler/script, then RouterOS runs it every minute at startup and reports CPU, memory, disk, traffic counters, uptime, RouterOS version, and active Hotspot/PPPoE counts directly over HTTPS. No VPS or separate computer is needed for these metrics. The app stores up to 35 days of samples and considers the router offline after 90 seconds without a report. Re-generate and paste the script if its token is rotated. The optional connector host is only needed for live per-user session details and remote disconnect commands.
10. The API connector is optional. To view per-user live sessions and issue remote disconnect commands, apply `20261008180000_add_router_api_connector.sql` and deploy the updated application. From a monitored router's **Users** tab, choose **Enable API connector**. It runs on an always-on host and makes outbound HTTPS requests to the billing app. If run off-site, connect that host to the router using a private VPN such as WireGuard; do not expose RouterOS management to the public internet.

    These `APP_URL=...` values are settings for the connector host; **do not paste them into RouterOS terminal**. On the VPS, create `/opt/router-connector` and give your SSH user write access. From the repository root in Windows PowerShell, upload the connector files with `scp connector\\agent.mjs connector\\Dockerfile connector\\compose.yaml connector\\.dockerignore connector\\.env.example ubuntu@<vps-ip>:/opt/router-connector/` (replace `ubuntu@<vps-ip>` with your VPS login). On the VPS, copy `.env.example` to `.env` and place the provided settings in that file. Set a dedicated RouterOS REST username/password and `ROUTER_REST_URL` to the router's private WireGuard DNS name/address ending in `/rest`. Use a certificate trusted by Node.js whose identity matches that hostname; if using a private CA, place its PEM file at `/etc/router-connector/router-ca.pem` on the VPS and set `NODE_EXTRA_CA_CERTS=/etc/router-connector/router-ca.pem` in `.env`. The Compose service mounts that directory read-only into the container. Never disable TLS verification. From `/opt/router-connector`, run `docker compose up -d --build`; inspect logs with `docker compose logs -f`. The included `connector/compose.yaml` runs with host networking so the container can use the VPS WireGuard route, restarts after process/host restarts, and drops Linux capabilities. Install/configure WireGuard as a host service enabled at boot before relying on monitoring. The connector retries outages with capped backoff. Keep `.env` and private keys off source control; rotate connector/API credentials if exposed.

    For initial testing before provisioning the VPS, the same Docker Compose service can be run on a Linux machine with the WireGuard route configured. Running it on a cloud VPS means it is independent of your personal computer; it still depends on the VPS, VPN, and Internet being available.

    On RouterOS 7.1+, configure HTTPS (`www-ssl`) with a certificate valid for the router's LAN/VPN DNS name. Restrict that service's **address** list to the connector's VPN tunnel address, not the public internet. For example, after installing the matching certificate, create a dedicated account with only the required policies and limit WebFig HTTPS to the VPN peer:

    ```routeros
    /user group add name=billing-connector policy=read,write,rest-api
    /user add name=billing-connector group=billing-connector password="<long-random-password>"
    /ip service set www-ssl disabled=no certificate="<router-certificate>" address=<connector-vpn-ip>/32
    ```

    Use a long random password, and add VPN-scoped input firewall rules if needed. Do not enable or forward RouterOS API/WinBox management ports from the WAN. The connector retries after outages with a capped backoff, reports sessions every five seconds while healthy, queues disconnect requests from the dashboard, and stores its RouterOS password only on the connector host.
11. To reconcile direct M-Pesa PayBill transfers, configure `C2B_CALLBACK_SECRET` as a random URL-safe server-only secret of at least 32 characters. **Payment settings** displays the workspace-specific validation and confirmation URLs to register for that Daraja shortcode; callback tokens are derived per tenant and the master secret is never sent to the browser. The confirmation endpoint matches the generated PPPoE account number and exact current-plan amount, extends expiry, and updates RADIUS atomically. Other payments are kept in **Billing → Payments** for an operator to match; a mismatched amount cannot activate service.
12. Set `CRON_SECRET` to a different random URL-safe secret of at least 32 characters. The included Vercel cron calls `/api/cron/expire-customers` daily at midnight UTC to mark expired accounts in the dashboard, which is compatible with Vercel Hobby. FreeRADIUS `Expiration` rules prevent new authentication at the configured expiry time; the daily job updates the dashboard status. The connector's session-disconnect action operates only on a currently reported RouterOS session.

The legacy `MPESA_*` environment configuration remains available only to the existing `default` workspace until its owner saves tenant-specific credentials. Newly created workspaces must configure their own Daraja account before paid checkout is available.

For subscriber operations, the **Subscribers** view supports tenant-scoped creation, manual suspension, and activation/renewal. New dashboard-created RADIUS logins start suspended with an `Auth-Type := Reject` rule; activate the account with a future expiry before service begins. Suspension adds the same reject rule; activation updates the expiry and removes it. STK callback payments and reconciled PayBill transfers update the account and expiry transactionally.

## Isolation

Staff API operations resolve tenant IDs from a live server-side session and membership. Package catalogs, purchases, customer records, RADIUS check/reply entries, portal branding, payment sessions, and router provisioning tokens are stored and queried with tenant ownership. Public portal routes resolve an active workspace by slug and scope all lookups to it. Unknown or inactive workspace slugs are rejected.

The current staff signup flow creates workspace owners; membership and session tables support additional roles and multiple memberships. Google sign-in requires a verified Google email; a verified Google identity can be linked to an existing account with the same email. This change does not add invitations or email verification.
