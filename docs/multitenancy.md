# ISP workspaces and tenant setup

Each ISP operates in a tenant workspace. Staff create an owner account at `/signup`, verify the email with the six-digit code sent to the address (valid for 10 minutes), and continue to `/get-started` to confirm the ISP and captive portal identity, configure M-Pesa Daraja (required before paid checkouts), create the first network site, and provision and confirm its MikroTik router. Verification codes can be resent after a one-minute cooldown and allow five attempts. Email-and-password sign-in is blocked until verification; verified Google sign-in continues directly to guided setup. The final checklist links to the dashboard and captive portal preview. Workspace sessions are opaque, HTTP-only cookies; changing an `x-tenant-id` header cannot change the selected workspace. Each user can create more than one workspace and switch between memberships.

## Workspace settings center

Apply `20261018200000_add_tenant_workspace_settings.sql` and `20261018210000_split_workspace_settings_storage.sql` before deploying the Settings center. Non-secret workspace preferences are stored per tenant. Passwords, provider tokens, and webhook signing secrets are encrypted with `TENANT_SECRETS_ENCRYPTION_KEY`; configure the same stable key in every environment that needs to save those credentials. Without the key, ordinary preferences and portal settings remain available, but generic secrets and Daraja/SMS credential changes are rejected rather than stored unencrypted.

The Settings center connects Branding and HotSpot portal name/copy to the live captive portal, Domain workspace-slug changes to the tenant record, Payments to Daraja settings, Communications to the Africa's Talking SMS configuration, and Profile/password changes to the authenticated account. Custom domains still require DNS and TLS setup at the hosting provider. SMTP, WhatsApp, AI, accounting, loyalty, operator-alert, developer-webhook, and message-template preferences can be saved, but external delivery, automation, token issuance, and template substitution are not enabled until their respective integrations are implemented. PPPoE options are workspace defaults only and do not alter existing plans or router provisioning. Two-factor authentication is not currently supported; the UI does not present it as enabled.

## Deploy

1. Apply all migrations in `supabase/migrations`, including `20261004120000_make_multitenant.sql`, before deploying the tenant-aware application. Existing billing, RADIUS, and provisioning rows remain assigned to the `default` workspace.
2. Keep `DATABASE_URL` configured on the server. For Vercel, use Supabase's **Transaction pooler** connection string (port 6543), not the Session pooler or direct database connection. The app limits each serverless process to one short-lived pooled connection, but the transaction pooler is still needed when Vercel runs many function instances. Account creation, sessions, workspace selection, billing, and password reset require the database. New passwords must be at least 6 characters and contain an uppercase letter, a number, and a symbol (maximum 128 characters). Email-and-password sign-in and signup work without Google OAuth credentials. To send signup verification codes and password-reset email, set the server-side `RESEND_API_KEY` to a Resend API key and `PASSWORD_RESET_FROM` to a sender address verified in Resend (for example, `LKTECH <noreply@example.com>`). Password reset additionally requires `APP_URL` to be the app's canonical origin (for example, `https://billing.example.com`); in local development, use `http://localhost:3000` for `APP_URL`. Apply `20261013100000_add_signup_email_verification.sql` before deploying email verification. Apply `20261004140000_add_password_reset_tokens.sql` before deploying password reset. Verification codes expire after 10 minutes and password reset links are single-use and expire after 30 minutes; resetting a password revokes the user's existing sessions.
3. Google sign-in is optional and is not shown on the login/signup pages by default. To enable it later, first apply `20261004130000_add_google_signin.sql`, then configure a Google OAuth 2.0 web application in Google Cloud Console and complete its consent-screen setup (publish the app or add each tester as a test user). Add the callback URI `https://<your-host>/api/auth/google/callback` to the OAuth client's authorized redirect URIs. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and the exact `GOOGLE_REDIRECT_URI` as server-only environment variables in every deployment environment. For local development, if `GOOGLE_REDIRECT_URI` is unset, the app derives it from the local origin; this project uses `http://127.0.0.1:3000/api/auth/google/callback`, which must also be registered as an authorized redirect URI. If using a different local host or port, set and register that exact callback URI.
4. To grant the existing operator access to migrated `default` workspace data, set `DEFAULT_TENANT_OWNER_EMAIL` to that operator's email before they create their first account through `/signup`. Only that exact email can claim the default workspace during signup. Without this setting, new signups create new isolated workspaces and existing rows stay in `default`.
5. Set `TENANT_SECRETS_ENCRYPTION_KEY` to a securely generated, stable 32-byte key (64 hexadecimal characters or base64). It encrypts workspace payment and SMS credentials, plus queued message contents. For example, generate one locally with:

   ```powershell
   node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
   ```

   Store it as a server-side production secret. Do not commit it, expose it as a `NEXT_PUBLIC_` variable, or change it without decrypting and re-encrypting every workspace's encrypted settings and queued messages.
6. Each workspace owner opens **Billing → Payment settings**, chooses the Daraja environment, and saves that ISP's consumer key, consumer secret, shortcode, passkey, and HTTPS callback URL. Credentials are encrypted with AES-256-GCM before storage. The callback URL must point to `/api/hotspot/daraja/callback` on this deployment. Secrets are never returned to the browser.
7. Apply `20261012120000_add_sms_notifications.sql` and `20261012130000_add_sms_delivery_reports.sql` to enable SMS. Each workspace owner opens **Billing → SMS settings**, chooses production or sandbox, and saves their Africa's Talking application username and API key. An approved sender ID is optional. The API key and queued message contents are encrypted using `TENANT_SECRETS_ENCRYPTION_KEY`. Configure Vercel Cron and `CRON_SECRET` for `/api/cron/send-sms` (the repository schedules it every five minutes); payment and service-status texts are attempted immediately and retried from the encrypted queue if delivery fails. To receive real delivery reports, configure a server-only `SMS_DELIVERY_REPORT_SECRET` with at least 32 URL-safe characters, set `APP_URL` to the public HTTPS app origin, then copy the callback URL shown in SMS settings into the Africa's Talking delivery-report callback configuration. The SMS panel shows queued, provider-accepted, delivered, and failed messages, report details, and lets staff resend failures without losing the original attempt. Use the test-message control to verify a recipient before enabling production messaging.
8. Give each captive portal its own workspace slug. Use a workspace subdomain where available, or add `?tenant=<workspace-slug>` to the portal URL. For example, `https://billing.example.com/hotspot?tenant=acme-network`. The provisioned MikroTik `login.html` opens the `/hotspot` subscription experience and carries the workspace, client MAC, and a return link to the router login. After purchase, customers can return to the captive sign-in form and enter the supplied credentials. The portal carries the workspace through package selection, checkout, reconnect, payment polling, and roaming API calls. Public tenant selection is for customer-facing portal requests only; it does not grant staff dashboard access.
9. For the guided MikroTik setup to create scripts, configure `PROVISIONING_ADMIN_KEY` as a server-only Vercel environment variable (at least 32 characters), `RADIUS_SERVER_ADDRESS` (an IPv4 address reachable from the router), `RADIUS_SHARED_SECRET` (16–64 letters, numbers, or hyphens), and `PROVISIONING_BASE_URL` (the app's HTTPS origin). Tenants never enter or receive the provisioning admin key; provisioning API requests use the signed-in workspace owner's/admin's session, and the server checks its own configured key. When the router is connected to the RADIUS host by WireGuard or another private VPN, set `RADIUS_SERVER_ADDRESS` to the host's private tunnel address and allow UDP 1812/1813 only over that private path; do not expose RADIUS to the public internet. If RADIUS must use a public address, restrict firewall ingress to the router's known public IP. The guided provisioning script requires RouterOS 7.1 or newer. The initial download link expires after 15 minutes; once the router reports the first setup script applied, the service-configuration step receives a fresh 24-hour window. That initial script reports the router's interface addresses so the service step can reject a Hotspot subnet that overlaps a selected WAN and reject a subscriber bridge address that overlaps the WAN network. Choose a private Hotspot subnet distinct from the WAN (for example, `172.31.0.0/24` when WAN uses `192.168.88.0/24`), keep the WAN port out of the subscriber bridge, and leave the router's local management port on the existing LAN bridge. The wizard isolates selected subscriber ports on a dedicated billing bridge, leaving unselected ports on the existing non-WAN LAN for regular unbilled internet; selected ports move only after confirmation. Move an active WAN DHCP client off the subscriber bridge before applying services; the wizard rejects using the same bridge for both roles. The router-specific service download rebuilds its script from the saved service choices using the current generator, so re-running the same configure command refreshes an older prepared script. The fetch command removes only the exact managed destination file before downloading its replacement. Existing routers must re-fetch the hotspot files to receive the subscription-portal redirect. Router monitoring is not installed by the provisioning script.
10. Apply `20261005150000_add_router_monitoring.sql` before deploying router monitoring. **Network → Devices → Routers** lists the configured network sites. Select a site and choose **Set up automatic monitoring** to generate a one-time authenticated RouterOS script. Copy/paste it into the MikroTik terminal once; it replaces the old monitor scheduler/script, then RouterOS starts the monitor automatically after reboot (with a short startup delay) and reports CPU, memory, disk, traffic counters, uptime, RouterOS version, and active Hotspot/PPPoE counts every 30 seconds directly over HTTPS. This lets monitoring recover after power is restored, once the router's internet uplink is back. No VPS or separate computer is needed for these metrics. The app stores up to 35 days of samples and considers the router offline after 90 seconds without a report. The monitor does not configure the ISP uplink: confirm its existing DHCP or PPPoE client and default route reconnect automatically. Re-run the generated script on previously configured routers to install the updated startup/retry cadence, and re-generate/paste it if the monitor token is rotated. The optional connector host is only needed for live per-user session details and remote disconnect commands.
11. The API connector is optional. To view per-user live sessions and issue remote disconnect commands, apply `20261008180000_add_router_api_connector.sql` and deploy the updated application. From a monitored router's **Users** tab, choose **Enable API connector**. It runs on an always-on host and makes outbound HTTPS requests to the billing app. If run off-site, connect that host to the router using a private VPN such as WireGuard; do not expose RouterOS management to the public internet.

    To show live per-subscriber speed, also apply `20261016120000_add_router_session_byte_counters.sql`, upload the latest `connector/agent.mjs`, and rebuild/restart the connector service on its host. The connector reports RouterOS active-session byte counters every five seconds; the browser checks for new samples every second and calculates Mbps from the actual counter/time deltas. Hotspot `bytes-in`/`bytes-out` are mapped to upload/download. If RouterOS does not expose counters for a session, speed remains unavailable rather than being estimated. When the connector is offline, the profile labels any available RADIUS values as a snapshot and does not present them as live speed. Existing connector instances do not update automatically when the web app is deployed.

    To enable the **Logs**, **Backups**, **Scheduler**, and **Script** tabs, also apply `20261012140000_add_router_resource_queries.sql`. These tabs fetch bounded live RouterOS REST results through the connector; scheduler commands and arbitrary script source are never returned. The Script tab shows the source of the LKTech-managed `lktech-monitor` script, with its router authentication token redacted. While the connector is online, it creates an LKTech-named binary RouterOS backup immediately if one does not exist, then at 24-hour intervals. Backups stay on the router; LKTech keeps the newest 30 automatic copies and the Backups tab lists the newest files first. Other files are not deleted. RouterOS backup files are unencrypted by default; optionally set `ROUTER_BACKUP_PASSWORD` in the connector host's `.env` to password-protect them, and keep that password safe because it is needed to restore those backups. RouterOS REST backup creation requires the connector user's existing `write` permission. **Payments** and summary cards use billing records assigned to the router's site and stored RouterOS telemetry. **Diagnosis** reports current telemetry checks. The connector must be online for live RouterOS resources and automatic backups to run.

    These `APP_URL=...` values are settings for the connector host; **do not paste them into RouterOS terminal**. On the VPS, create `/opt/router-connector` and give your SSH user write access. From the repository root in Windows PowerShell, upload the connector files with `scp connector\\agent.mjs connector\\backup-policy.mjs connector\\router-script-source.mjs connector\\Dockerfile connector\\compose.yaml connector\\.dockerignore connector\\.env.example ubuntu@<vps-ip>:/opt/router-connector/` (replace `ubuntu@<vps-ip>` with your VPS login). On the VPS, copy `.env.example` to `.env` and place the provided settings in that file. Set a dedicated RouterOS REST username/password and `ROUTER_REST_URL` to the router's private WireGuard DNS name/address ending in `/rest`. If the router certificate uses a DNS name that resolves publicly while the router is reachable only over VPN, add a Compose `extra_hosts` entry mapping that DNS name to the router's private VPN IP; use the DNS name in `ROUTER_REST_URL` so TLS hostname verification remains enabled. Use a certificate trusted by Node.js whose identity matches that hostname; if using a private CA, place its PEM file at `/etc/router-connector/router-ca.pem` on the VPS and set `NODE_EXTRA_CA_CERTS=/etc/router-connector/router-ca.pem` in `.env`. The Compose service mounts that directory read-only into the container. Never disable TLS verification. From `/opt/router-connector`, run `docker compose up -d --build`; inspect logs with `docker compose logs -f`. The included `connector/compose.yaml` runs with host networking so the container can use the VPS WireGuard route, restarts after process/host restarts, and drops Linux capabilities. Install/configure WireGuard as a host service enabled at boot before relying on monitoring. The connector retries outages with capped backoff. Keep `.env` and private keys off source control; rotate connector/API credentials if exposed.

    For initial testing before provisioning the VPS, the same Docker Compose service can be run on a Linux machine with the WireGuard route configured. Running it on a cloud VPS means it is independent of your personal computer; it still depends on the VPS, VPN, and Internet being available.

    On RouterOS 7.1+, configure HTTPS (`www-ssl`) with a certificate valid for the router's LAN/VPN DNS name. Restrict that service's **address** list to the connector's VPN tunnel address, not the public internet. For example, after installing the matching certificate, create a dedicated account with only the required policies and limit WebFig HTTPS to the VPN peer:

    ```routeros
    /user group add name=billing-connector policy=read,write,rest-api
    /user add name=billing-connector group=billing-connector password="<long-random-password>"
    /ip service set www-ssl disabled=no certificate="<router-certificate>" address=<connector-vpn-ip>/32
    ```

    The dashboard's **Open web console** link uses the router's reported WireGuard address and the enabled WebFig service port. Regenerate and install the monitor script after adding the WireGuard peer, then wait for its next report before using the link. Open it from a device connected to the same WireGuard tunnel, and allow only the required VPN client addresses in the service and input firewall. Never expose WebFig, RouterOS API, or WinBox management ports to the WAN.

    Use a long random password, and add VPN-scoped input firewall rules if needed. The connector retries after outages with a capped backoff, reports sessions every five seconds while healthy, queues disconnect requests from the dashboard, and stores its RouterOS password only on the connector host.
11. To reconcile direct M-Pesa PayBill transfers, configure `C2B_CALLBACK_SECRET` as a random URL-safe server-only secret of at least 32 characters. **Payment settings** displays the workspace-specific validation and confirmation URLs to register for that Daraja shortcode; callback tokens are derived per tenant and the master secret is never sent to the browser. The confirmation endpoint matches the generated PPPoE account number and exact current-plan amount, extends expiry, and updates RADIUS atomically. Other payments are kept in **Billing → Payments** for an operator to match; a mismatched amount cannot activate service.
12. Set `CRON_SECRET` to a different random URL-safe secret of at least 32 characters. The included Vercel cron calls `/api/cron/expire-customers` daily at midnight UTC to mark expired accounts in the dashboard, which is compatible with Vercel Hobby. FreeRADIUS `Expiration` rules prevent new authentication at the configured expiry time; the daily job updates the dashboard status. The connector's session-disconnect action operates only on a currently reported RouterOS session.

The legacy `MPESA_*` environment configuration remains available only to the existing `default` workspace until its owner saves tenant-specific credentials. Newly created workspaces must configure their own Daraja account before paid checkout is available.

For subscriber operations, the **Subscribers** view supports tenant-scoped creation, manual suspension, activation/renewal, and CSV import/export. Export includes subscriber contact, plan, status, and expiry details but intentionally leaves RADIUS passwords blank. Imports require a password for each row, an enabled workspace plan, and a unique RADIUS username; each successful import creates the corresponding RADIUS rules and starts suspended. Imports accept up to 200 rows at a time and report row-level failures without stopping other records. Exports include up to 10,000 workspace subscribers.

New dashboard-created RADIUS logins start suspended with an `Auth-Type := Reject` rule; activate the account with a future expiry before service begins. Suspension adds the same reject rule; activation updates the expiry and removes it. STK callback payments and reconciled PayBill transfers update the account and expiry transactionally.

## Isolation

Staff API operations resolve tenant IDs from a live server-side session and membership. Package catalogs, purchases, customer records, RADIUS check/reply entries, portal branding, payment sessions, and router provisioning tokens are stored and queried with tenant ownership. Public portal routes resolve an active workspace by slug and scope all lookups to it. Unknown or inactive workspace slugs are rejected.

The current staff signup flow creates workspace owners; membership and session tables support additional roles and multiple memberships. Google sign-in requires a verified Google email; a verified Google identity can be linked to an existing account with the same email. This change does not add invitations or email verification.
